# 风味考古局离线数字博物馆全面优化设计

日期：2026-07-14  
状态：已确认，等待实施计划  
优化目标：在保留现有离线能力、数据资产与可信边界的前提下，大幅重做产品体验，使其同时具备专业数字博物馆的可信感与风味考古实验室的操作感。

## 1. 背景与现状

现有离线版本已经具备单文件构建、40 道馆藏、五步可信复原、Three.js 蟹酿橙展台、WebGL 降级视图、离线规则、证书与商业合作展厅。当前 38 项离线测试通过，单文件构建成功，运行时未发现阻断性控制台错误。

本轮优化不再以补齐基础功能为主，而是解决以下完成度问题：

- 首屏品牌、入口、3D 和说明彼此分散，视觉焦点不够集中。
- 五步复原以页面内容替换为主，证据、模型和结论之间的连续关系较弱。
- 3D 蟹酿橙造型、材质、灯光和热点标注仍接近功能原型。
- 馆藏、问答、风味进化和玩法之间缺少共享菜品上下文。
- 深色界面层级单一，证据文本的可读性和专业展陈质感不足。
- 现有测试偏向源码结构检查，需要增加真实交互与浏览器验收。

## 2. 已确认的决策

- 优化范围为全面优化，覆盖评审叙事、视觉交互、功能完整性、性能与兼容性。
- 允许大幅重做界面与交互，仅保留核心创意、可信数据和有效规则资产。
- 产品气质采用“当代数字博物馆 + 风味考古实验室”。
- 方案采用“叙事展厅 + 推演工作台”：首页建立品牌与可信感，核心流程进入连续实验台。
- Codex 可以直接修改、测试和交付代码，但这些改动不得作为 TRAE 开发证据。
- 最终离线交付仍为可双击运行的单个 `offline.html`。
- 最终 `offline.html` 的实际文件大小必须小于或等于 3,000,000 字节（十进制 3 MB），不能以 gzip 后体积替代。

## 3. 产品目标

评委首次打开页面后，应在 10 秒内理解三件事：

1. 这是“风味考古局”，不是通用菜谱或图片生成工具。
2. 核心产品是一套基于文献证据的失传菜复原方法。
3. 这套能力可以落地为博物馆互动展项。

评委应能在 90 秒内完成蟹酿橙标杆流程，并形成两层判断：

- 可信判断：复原结论有出处、有证据类型、有不确定性边界。
- 落地判断：3D 藏品、馆藏库与互动研究已经构成可部署的展陈产品。

## 4. 信息架构

应用使用一个连续的数字博物馆壳层，不使用需要服务器回退的 URL 路由。

一级目的地收敛为：

- `可信复原台`
- `风味馆藏库`
- `合作展厅`

原有能力重新归类如下：

| 现有能力 | 新位置 | 上下文关系 |
| --- | --- | --- |
| 五步可信复原 | 可信复原台 | 围绕当前复原会话运行 |
| 40 道档案与味觉星图 | 风味馆藏库 | 负责选择当前菜品 |
| 数字传承人问答 | 馆藏库 / 互动研究 | 继承当前菜品 |
| 风味进化 | 馆藏库 / 互动研究 | 继承当前菜品并选择第二道菜 |
| 真假非遗、每日复活、拍照认祖、证书 | 馆藏库 / 互动研究 | 共享进度与馆藏数据 |
| 商业合作 | 合作展厅 | 承接复原结果与展项规模 |

桌面端采用左侧品牌与主导航、顶部当前展厅状态、中央主内容区。移动端采用顶部品牌栏和底部主导航，内容区按单列排列。

离线模式、研究声明、数据边界和当前进度进入持续可见但低干扰的状态栏，不占据首屏主视觉中心。

## 5. 首页设计

首页第一屏直接显示真实可操作的蟹酿橙 3D 藏品。品牌名、产品定位与主操作叠加在场景上，不放入卡片，也不使用营销式左右分栏。

首屏内容包括：

- 品牌名：`风味考古局`
- 定位：`以文献为证，复原失传中国味道`
- 主操作：`开始可信复原`
- 次操作：`浏览风味馆藏`
- 三个编号证据热点，对应橙壳、蟹馅与蒸制结构
- 低干扰的离线与研究边界状态

首屏高度应在桌面与移动视口中露出下一段内容的提示。下一段展示《山家清供》原句、三项证据摘要、40 道馆藏规模和进入复原台的连续入口。

## 6. 可信复原台

可信复原台是一套连续工作台，3D 藏品在五个阶段中保持存在，周围信息随阶段变化。

桌面布局：

- 左侧：五步进度、当前任务和完成状态。
- 中央：全宽、无装饰性卡片边框的 3D 藏品场景。
- 右侧：证据记录仪，显示当前热点对应的原文、来源、类型、可信度、争议和解释。
- 底部：当前阶段的主要操作与上一步、下一步。

移动布局依次为场景、当前任务、证据面板。主要操作固定在底部安全区内，但不得遮挡 3D 控件、正文或系统导航区域。

### 6.1 装入历史线索

保留自由输入与蟹酿橙预置线索。匹配后把朝代、地域、食材、器皿和技法拆为可见证据标签。弱线索必须返回“证据不足”，列出仍需补齐的线索类别，不得默认加载蟹酿橙。

### 6.2 古籍解码

突出《山家清供》原句，并把识别出的证据标签按来源关系连接到模型区域。文献直接支持与规则提取必须使用不同状态表达。

### 6.3 证据推演

三个核心证据依次点亮。点击热点后，右侧证据记录仪就地更新，不使用遮挡主场景的全高抽屉。证据类型统一为文献明确记载、跨资料推断、现代转译、证据不足和待专家复核。

### 6.4 结构复原

提供恢复视角、结构拆解、历史结构和现代成品四类控制。模型材质与证据覆盖同步变化。热点必须可通过鼠标、触控和键盘访问。

### 6.5 复原结论

最终生成一份四区复原档案：

- 历史复原结论
- 现代厨房转译
- 不可确认项
- 证据覆盖率与来源摘要

历史结构与现代转译切换时，模型和文字同步高亮发生调整的位置。结论页首先提供保存或打印复原档案，其次引导查看馆藏库和合作展厅。

## 7. 风味馆藏库

馆藏库使用朝代时间轴与可扫描列表替代当前均匀星点网格。保留朝代、档案状态与关键词筛选，40 道菜全部可访问。

每个列表项只展示菜名、朝代、地域、技法和档案状态。选择后打开详情区，展示较大菜品图、原文短摘、来源、风味、技法、证据状态和研究说明。

馆藏库包含两个标签页：

- `馆藏档案`：时间轴、筛选、列表和详情。
- `互动研究`：考据问答、风味进化、真假非遗、每日复活、拍照认祖与证书。

互动研究继承当前选中菜品。没有选中菜品时，界面明确要求先选择馆藏，不静默使用固定默认值。需要两道菜的风味进化只额外选择第二道菜。

## 8. 合作展厅

合作展厅使用展项规格与实施流程表达商业价值，不使用营销式卡片堆叠或泛化口号。

内容包括：

- 适用场景与设备
- 一道标杆菜试点包的交付范围
- 2 至 4 周实施时间轴
- 内容、技术与研学交付物
- 完成率、停留时间、热点点击率和研学任务完成率等指标
- 离线部署、内容边界和后续扩展方式

合作展厅应承接用户刚完成的蟹酿橙流程，以“把这套复原体验带进博物馆”为结论，而不是单独销售另一套产品。

## 9. 视觉系统

视觉采用深色展厅与暖白考据纸面的双层系统：

- 近黑墨色：展厅与 3D 场景背景。
- 暖白：主要文字与证据纸面。
- 朱砂红：主操作、文献原句和重要警示。
- 青铜绿：可信证据与完成状态。
- 琥珀金：选中热点、复原进度和藏品高光。

不得使用大面积单一色相、装饰性渐变光球、粒子团、繁复仿古纹样或漂浮页面卡片。证据纸面使用浅底深字，使文献内容与深色场景形成明确层级。

标题使用本地中文宋体或系统衬线字体，正文与数据使用本地黑体。字体大小使用稳定的响应式层级，不随视口宽度连续缩放，字距保持为零。

按钮圆角为 6 至 8 像素。熟悉的模型控制使用本地打包的 Lucide 图标，并提供可读标签或工具提示。命令按钮只保留清晰动作文本。

## 10. 3D 藏品设计

蟹酿橙 3D 场景继续使用本地 Three.js 与程序化几何，不引入在线模型、外部贴图或 CDN。

模型改进包括：

- 更接近真实橙形的非完全球体轮廓与橙皮粗糙度。
- 清晰的截顶结构、橙盖厚度和内部橙壳。
- 可辨认的蟹肉与蟹膏填充层，而不是单一球体。
- 轻量蒸具或承托结构，帮助理解“入甑蒸熟”。
- 更自然的灯光、阴影和材质对比，同时控制几何复杂度。

热点改为编号、细线和锚点组成的展陈标注，不再固定为画布四角的浮动按钮。热点选择、模型局部高亮与证据记录仪保持同步。

WebGL 不可用、初始化失败或上下文丢失时，切换为同样信息结构的分层剖面视图。降级视图必须保留三个热点、历史与现代状态、结构拆解和证据说明。

## 11. 状态与数据流

应用使用统一复原会话状态，包含：

- 当前一级目的地与馆藏标签页
- 当前菜品与风味进化第二菜品
- 当前复原阶段
- 线索文本与匹配结果
- 已查看证据与证据覆盖率
- 模型模式、拆解状态和选中热点
- 已完成任务与用户偏好

只有当前菜品、完成步骤、减少动态偏好和必要进度可以持久化。用户上传图片只在内存中处理，刷新后清除。

现有 40 道馆藏数据、蟹酿橙证据、题库、问答、进化规则、每日规则、证书逻辑和用户未提交的数据修订必须保留。允许补充展示字段和关系字段，但不凭空补造文献证据。

## 12. 组件边界

- `MuseumShell`：品牌、主导航、状态栏、响应式布局。
- `HomeExhibit`：首屏藏品、品牌信号和两条入口。
- `RestorationWorkbench`：五步状态机和阶段操作。
- `WorkflowRail`：阶段、任务和完成状态。
- `CrabOrangeScene`：Three.js 创建、交互、动画与资源释放。
- `EvidenceInspector`：证据详情、状态说明和争议信息。
- `RestorationReport`：历史、现代、未知项和证据覆盖。
- `ArchiveLibrary`：时间轴、筛选、列表和详情。
- `ResearchLab`：问答、进化与互动玩法容器。
- `PartnershipExhibit`：试点规格与实施时间轴。

场景组件不得直接决定业务阶段，证据面板不得读取 Three.js 内部状态。它们通过复原会话中的选中热点、模型模式和证据进度通信。

## 13. 性能预算

最终 `offline.html` 的实际大小必须小于或等于 3,000,000 字节（十进制 3 MB）。

预算控制措施：

- 40 张馆藏图继续使用压缩后的 WebP 数据，并按实际视觉尺寸重新评估质量。
- 首屏只创建蟹酿橙场景，不创建或解码其余馆藏图。
- 馆藏图片只在列表项或详情真正可见时进入 DOM。
- 3D 材质优先使用程序化参数，不增加大体积贴图。
- 图标库只导入实际使用的图标，避免整库打包。
- 合并重复样式和组件逻辑，删除旧离线界面中不再使用的代码。
- 构建门禁直接读取最终 HTML 字节数，超过 3,000,000 字节时失败。

## 14. 异常与降级

- WebGL 创建失败、运行异常或上下文丢失：自动切换分层剖面视图。
- 本地存储不可用或写入失败：关闭持久化并继续当前会话。
- 证书下载受限：提供打印视图与截图提示。
- 线索不足：显示缺失类别，不输出确定复原结论。
- 图片解码失败：显示包含菜名和档案状态的稳定占位区域。
- 页面组件异常：错误边界提供“恢复当前展厅”和“返回首页”。
- 减少动态效果：取消非必要过渡，模型状态立即到达目标位置。

所有异常提示必须说明仍可执行的下一步，不使用模糊的“发生错误”。

## 15. 测试与验收

### 15.1 自动化测试

- 保留并更新现有 38 项离线测试。
- 为统一复原状态、共享当前菜品、证据记录仪、馆藏筛选和异常降级增加单元测试。
- 为首页、五步复原、3D 热点、馆藏详情、互动研究和合作展厅增加组件交互测试。
- 增加真实浏览器端到端测试，覆盖 WebGL 正常与强制失败两条路径。
- 构建测试验证单文件、无远程资源、无运行时网络请求和不超过 3,000,000 字节。

### 15.2 视口与可访问性

至少验证以下视口：

- 1440 × 900
- 1280 × 720
- 390 × 844

每个视口检查横向滚动、文字溢出、控件遮挡、固定操作区与系统安全区。关键导航、阶段操作、热点和证据面板必须支持键盘访问，并有清晰焦点状态。证据状态不能只依靠颜色区分。

### 15.3 完成门槛

只有同时满足以下条件，优化才算完成：

1. Edge 与 Chrome 可从本地 `offline.html` 完成五步主流程。
2. 3D 场景非空白、构图正确、可旋转、可拆解且三个热点有效。
3. 强制 WebGL 失败后仍可完成主流程并查看三项证据。
4. 40 道馆藏均可搜索、筛选和打开详情。
5. 互动研究继承当前菜品，页面刷新和返回展厅不破坏关键进度。
6. 三种目标视口无不合理重叠、溢出或被遮挡控件。
7. 控制台无未处理异常，运行期间不发起网络请求。
8. 最终 `offline.html` 实际大小不超过 3,000,000 字节。
9. 原在线 React 应用的现有构建与测试不回归。

## 16. TRAE 证据边界

本轮 Codex 优化获得直接修改代码的授权，但不得把 Codex 会话、改动记录、截图或验证输出伪装为 TRAE 开发证据。

`docs/competition/trae-evidence-manifest.json` 中只允许记录真实 TRAE Session ID、TRAE 任务截图和对应的 TRAE 验证记录。Codex 优化可以在产品变更说明中如实记录，但不能补齐或替代参赛规则要求的 TRAE 取证。

## 17. 非目标

本轮不做：

- 在线大模型或图片生成调用。
- 服务端、数据库或登录系统接入离线版。
- 影视级高精度 3D 建模或大型贴图资产。
- 新增未经核验的文献结论。
- 为 40 道菜全部制作与蟹酿橙同等复杂的 3D 模型。
- 把 Codex 实施过程包装为 TRAE 实践过程。
- 为博物馆大屏另做独立版本。
