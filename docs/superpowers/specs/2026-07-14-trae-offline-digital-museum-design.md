# 风味考古局 TRAE 初赛离线数字博物馆设计

日期：2026-07-14  
状态：已完成访谈确认，待用户审阅书面规格  
目标：以专业评审晋级为第一优先级，交付可断网运行的交互式 HTML ZIP 与完整参赛材料

## 1. 背景与参赛约束

风味考古局已有 React 前端、Node 后端、Python 复原服务、40 道风味档案、蟹酿橙标杆案例，以及数字传承人、味觉星图、风味进化、轻量玩法和商业价值页面。本轮不是重新发明产品，而是把现有能力收敛为一条评委能在 90 秒内理解的主线，并改造成不依赖服务器和外部 API 的离线参赛版本。

初赛交付必须满足以下六项硬门槛：

1. 提供 ZIP 打包的交互式 HTML，解压后可直接打开。
2. Demo 核心功能可交互、能够真实体验。
3. 作品帖包含 Demo 简介、创作思路、体验方式和 TRAE 实践过程。
4. 提供不少于 3 张 TRAE 开发关键步骤截图。
5. 提供不少于 3 个真实 TRAE 关键任务 Session ID。
6. 附上审核通过的报名帖链接。

报名帖链接当前尚未提供。作品帖中使用醒目占位符 `【待补：审核通过的报名帖链接】`，但最终提交检查必须将其视为阻断项，不得带占位符提交。

## 2. 产品定位

风味考古局是一座可离线体验的数字风味博物馆，其核心能力是：

> 输入一段古籍、古画描述或口述线索，通过可追溯的证据链，复原一道失传菜的历史形态，并转译为现代可执行版本。

产品的核心定位是“非遗饮食 AI 复原引擎”，首要落地场景是文博互动展陈，第二落地场景是研学课程。网页的第一观看者是比赛评委，核心体验模拟博物馆观众，商业价值页面负责承接博物馆采购与合作判断。

评委完成体验后应形成两层结论：

- 核心信任：复原过程可追溯、可复核，并诚实展示不确定性。
- 落地判断：这套能力已经可以成为博物馆互动展项。

产品不声称替历史下定论，也不把离线预置数据伪装为实时 AI。其差异点不是“更会写菜谱”，而是把文献、食材、技法、时代地域约束和现代转译放进同一条可见证据链。

## 3. 目标用户与商业路径

第一目标客户是博物馆、非遗馆的策展与教育部门。第一款可售产品是博物馆互动展项试点包：选定一座机构和一道地方历史名菜，在 2 至 4 周内交付可在触摸屏、大屏或展台运行的复原互动体验。

试点交付物包括：

- 一道标杆菜的结构化证据档案。
- 轻量 3D 数字藏品模型与证据热点。
- 可信复原互动流程。
- 历史复原与现代厨房转译内容。
- 研学任务单与教学扩展材料。
- 可评估的现场数据指标设计。

建议评估指标包括体验完成率、平均停留时间、证据热点点击率和研学任务完成率。研学课程包是第二阶段标准化产品，用于复用一次性展项中的内容资产并形成复购。

## 4. 整体方案与信息架构

采用“数字博物馆型”方案。最终离线版本是单文件沉浸式应用，展厅之间通过应用状态切换，不使用依赖服务器回退的页面路由。

首页只提供两条路线：

- 主入口：`开始 90 秒可信复原`
- 次入口：`自由探索馆藏`

一级导航收敛为：

- `可信复原`
- `探索馆藏`
- `商业合作`

“探索馆藏”保留全部原有能力：

- 数字传承人
- 味觉星图
- 风味进化
- 拍照认祖
- 每日复活
- 真假非遗
- 40 道风味档案
- 分享证书

完成核心复原后，根据当前菜品和操作上下文推荐下一站，但不强制跳转。用户始终可以通过“探索馆藏”直接访问全部功能。

## 5. 90 秒评委主流程

### 5.1 装入历史线索

评委主路线默认装入《山家清供》蟹酿橙短摘，同时保留自由输入。界面必须明确标注“离线评审模式”，说明标杆案例来自内置证据库。

### 5.2 古籍解码

系统从本地结构化数据中提取时代、地域、食材、器皿和技法。自由输入采用浏览器本地关键词与规则匹配，只在内置证据库覆盖范围内输出结果。

### 5.3 证据推演

主流程依次展示古籍解码、食材校验、技法推演和成品复原。主界面只展示 3 至 5 条关键证据；完整原文短摘、出处、推断类型、版权说明和争议点进入“考据档案”抽屉。

### 5.4 3D 复原

中央蟹酿橙以轻量“博物馆数字藏品”呈现。模型从证据线框逐步恢复材质，支持旋转、缩放、自动回正和结构拆解。

三个关键热点为：

- 橙壳：`以橙为器`
- 蟹馅：`以蟹膏肉实其内`
- 蒸制结构：`覆橙顶，入甑蒸熟`

点击热点时，模型局部高亮，并显示原文短摘、来源、证据类型和置信状态。3D 必须服务于证据理解，而不是作为装饰性首屏动画。

### 5.5 双版本结果

结果页并列展示：

- 历史复原档案：说明当时可能怎样制作，并保留不确定性。
- 现代厨房转译：说明替代食材、现代设备、食品安全调整和调整原因。

不可确认内容单独列出，不能用现代常识悄悄补齐历史。3D 可切换历史结构与现代成品状态，查看发生调整的位置。

### 5.6 商业承接

主流程结束后首先展示“把这道菜带进博物馆”的试点方案，而不是直接展示联系方式。页面说明适用设备、交付内容、2 至 4 周周期、评估指标和研学扩展，然后提供“查看全部馆藏”“查看技术可信说明”“商业合作”入口。

## 6. 证据与信任设计

证据采用分层展示，并统一使用以下状态：

- `文献明确记载`：原文直接支持。
- `跨资料推断`：由多个来源共同支持。
- `现代转译`：为今天可执行而作出的调整。
- `证据不足`：不输出确定结论。
- `待专家复核`：允许查看，但不能作为定论。

弱线索必须返回“证据不足”，同时提示用户至少补充古籍原文或口述来源、大致朝代地域，以及一个可验证的食材或技法。离线规则、预置案例、推测结果与专家复核状态必须在界面上可区分。

素材版权采用“自有视觉为主，权威资料只作短摘与来源引用”的边界：

- 蟹酿橙主视觉、3D 模型和馆藏图片使用项目自有或 AI 生成素材。
- 古籍仅展示必要短摘、书名、来源和访问地址。
- 权威网站实物图只用于内部形态研究，不直接嵌入参赛作品。
- 页面增加“研究性复原，不替代学术定论”的说明。

## 7. 原有功能的离线闭环

### 7.1 数字传承人

围绕标杆菜提供本地多轮问答，覆盖历史背景、食材、技法和现代做法。默认静音，用户主动播放离线语音，所有讲解均提供完整字幕。音频不可用时，文字能力保持完整。

### 7.2 味觉星图

保留 40 道风味档案，支持按朝代、地域、技法和风味筛选。档案分为“证据完整”“推荐考据”“资料待补”三种状态，不能暗示 40 道菜都已完成同等强度的可信复原。

### 7.3 风味进化

用户选择两道菜后，本地规则根据食材、技法、地域和时代约束生成融合方向，并展示继承关系、现代创新点和风险提示。结果明确标注为离线规则推演。

### 7.4 拍照认祖

用户选择本地菜品图片后，通过浏览器本地文件信息、轻量图像特征和用户补充选项匹配内置风味谱系。无法可靠判断时标注“离线推测”或要求用户补充信息，不上传图片。

### 7.5 每日复活

从本地种子库抽取一道历史菜，用户完成线索解谜后解锁档案。离线环境中的“每日”以本地日期生成稳定结果。

### 7.6 真假非遗

使用内置题库完成判断。每题回答后立即展示正确答案、文献依据和证据状态。

### 7.7 分享证书

根据用户完成的复原任务在本地生成证书，支持下载或打印，不上传用户数据。若浏览器限制直接下载，则提供打印与截图降级方案。

### 7.8 商业合作

展示博物馆互动展项试点包、研学扩展包、交付周期、适用设备、评估指标和服务边界，不把页面做成报价单或泛化销售宣传页。

所有展厅共享同一套菜品、证据、用户进度和状态数据，避免形成彼此割裂的小游戏集合。

## 8. 视觉与交互设计

视觉采用“当代数字博物馆”为主体，融合古籍档案的信息语言和少量 AI 推理动态反馈。

### 8.1 色彩

- 深墨黑与炭灰：展厅空间。
- 暖白：正文与主要信息。
- 朱砂红：文献出处与关键证据。
- 青铜绿：可信状态。
- 琥珀金：复原完成状态。

避免大面积科技蓝、单一色相、渐变光球、装饰性粒子团和繁复仿古纹样。

### 8.2 字体与排版

- 标题采用克制的中文宋体或现代衬线体。
- 正文和数据采用清晰中文黑体。
- 证据卡借鉴博物馆藏品标签，不做仿古卷轴。
- 书名、原文短摘、推断、现代转译和风险提示形成明确层级。
- 所有文字在桌面与手机端不得溢出、遮挡或与 3D 控件重叠。

### 8.3 动效

- 证据成立时，节点依次点亮并连接至 3D 热点。
- 3D 模型从线框过渡至完整材质。
- 展厅切换采用短暂淡入与空间位移。
- 提供跳过动效，尊重系统减少动态效果设置。
- 不使用不可跳过的片头或自动播放音频。

## 9. 离线技术架构

最终交付为 ZIP 包内的单个主 HTML。解压后双击即可运行，不依赖服务器、数据库、外部 API、CDN 或网络字体。

技术边界如下：

- React 管理界面与展厅状态。
- Three.js 渲染 3D 蟹酿橙。
- 菜品、证据、问答、题库和本地规则以内嵌结构化数据提供。
- 图片、字体、必要语音与 3D 资源经过压缩后嵌入构建产物。
- 不使用需要服务端回退的 BrowserRouter 深层路由。
- 进度、偏好和证书信息仅保存在本地浏览器。
- 不声称离线版本正在调用实时 AI。

40 道馆藏全部保留，每道只使用一张优化后的 WebP；蟹酿橙主视觉与 3D 贴图保留较高质量。首屏资源优先解码，其他馆藏图片进入相应展厅时再解码。

## 10. 降级与异常处理

- 3D 初始化失败时，展示可交互的分层 2.5D 备用视图。
- 音频失败时，字幕和问答保持完整。
- 下载证书受限时，提供打印与截图方式。
- 自由输入无法匹配证据时，返回“证据不足”而不是默认第一道菜。
- 浏览器不支持某项能力时，展示具体降级状态和仍可用的操作。
- 用户图片只在本机处理，不上传、不长期保存。
- 页面刷新、返回展厅和重复体验不应破坏关键流程。

## 11. 设备、语言与无障碍

本次初赛离线版只提供中文。原在线项目的双语能力继续保留，但不纳入离线参赛版范围。

桌面端是主评审体验，重点适配 1280 至 1920 像素宽度。手机端保留全部功能入口与可完成操作，采用纵向布局并降低同时显示的信息量。博物馆大屏只作为商业方案展示，不在本轮单独开发一套界面。

交互要求包括：

- 3D 支持鼠标拖拽与触控旋转、缩放。
- 图标按钮有可读标签或工具提示。
- 键盘可访问关键导航与操作。
- 颜色之外还要使用文字或图标表达证据状态。
- 支持减少动态效果。
- 音频内容始终有字幕。

## 12. 性能与兼容验收

必须通过以下产品验收：

1. 断网后双击主 HTML，核心功能可运行。
2. 90 秒主流程能从线索输入完整走到商业承接。
3. 3D 支持旋转、缩放、热点、结构拆解和降级视图。
4. 自由输入能匹配已知线索，弱线索返回证据不足。
5. 所有原有功能均能完成一次离线闭环。
6. Chrome 与 Edge 当前稳定版无阻断错误。
7. 桌面和手机视口无文字溢出、控件遮挡或不合理重叠。
8. ZIP 解压至包含中文或空格的路径后仍可运行。
9. 控制台无未处理异常，资源无缺失，版权标注完整。
10. 3D 交互无明显卡顿，首屏不等待全部馆藏图片解码。

## 13. TRAE 实践与取证计划

在设计规格获得书面批准后，使用桌面 TRAE Work CN 创建三个真实开发任务：

### 任务一：离线数字博物馆与功能闭环

完成单文件展厅架构、90 秒主流程、内置数据、全部原有功能离线闭环和中文桌面优先响应式布局。

### 任务二：3D 蟹酿橙与证据热点

完成 Three.js 轻量模型、线框到材质过渡、旋转缩放、结构拆解、三个证据热点和 2.5D 降级视图。

### 任务三：验证、优化与提交包

完成断网、Chrome、Edge、中文路径、手机视口、资源完整性和控制台检查；优化文件体积与加载性能；生成最终 ZIP 和作品帖材料。

每个任务都必须保存：

- 一个真实 TRAE Session ID。
- 至少一张能清楚显示任务内容与执行过程的截图。
- 对应代码改动与验证结果。

最终作品帖使用不少于 3 张关键步骤截图和不少于 3 个 Session ID。项目自身的教学会话 ID、Codex 任务 ID 或伪造字符串均不得替代 TRAE Session ID。

## 14. 作品帖结构

最终作品帖至少包含：

### Demo 简介

- 一句话产品形态。
- 第一目标用户。
- 可信复原、3D 证据展台和数字馆藏三项核心能力。
- 最终界面截图。

### Demo 创作思路

- 非遗饮食资料分散、传统展陈缺少参与感、普通生成式 AI 难以说明来源的真实痛点。
- 为什么选择“证据化复原”而不是普通菜谱生成。
- 为什么以博物馆互动展项作为第一落地场景。

### Demo 体验方式

- 上传最终 ZIP。
- 明确写明“解压后双击主 HTML，无需联网”。
- 说明推荐使用 Chrome 或 Edge 桌面版。

### TRAE 实践过程

- 任务如何拆分。
- 关键实现与取舍。
- 遇到的问题及修复。
- 最终验证结果。
- 不少于 3 张开发步骤截图。
- 不少于 3 个真实 Session ID。
- 审核通过的报名帖链接。

| 门槛 | 当前状态 | 完成条件 |
| --- | --- | --- |
| 可交互离线 HTML 与 ZIP | 待完成 | 断网双击主 HTML 通过全部核心验收，ZIP 可正常解压 |
| 核心功能真实可体验 | 待完成 | 主流程与全部原有功能均能完成离线闭环 |

## 16. 非目标

本轮明确不做：

- 离线运行真实大模型或图片生成模型。
- 影视级高精度 3D 建模。
- 完整 3D 历史厨房游戏。
- 强制制作完整演示视频。
- 独立博物馆大屏版本。
- 新增英文离线版本。
- 把 40 道菜全部补齐为与蟹酿橙同等证据强度。
- 将未核验的网络图片直接嵌入参赛作品。

这些边界用于保障专业评审所需的创新性、真实价值、完成度和可靠交付。
