# 风味考古局策展委托首页与菜品融合设计

## 背景与目标

当前离线体验已经具备可信复原、40 道馆藏、Three.js 证据展台、菜品融合和博物馆合作方案，但首页只突出单道蟹酿橙与两个常规入口。评委在第一屏看不到产品从历史证据走向新菜研发与数字展项交付的完整闭环，也无法快速判断谁会使用、为什么现有工具不能替代、最终交付物是什么。

本轮改造以博物馆和非遗馆策展人为第一服务对象，把首页从品牌展示页改为正在办理的“策展委托现场”。核心主张是“从复原到新生”：先以古籍证据复原失传菜，再在真实古菜血统和规则约束下融合出可进入展项的新菜方向。

## 产品定位

- 第一用户：博物馆、非遗馆的策展人与教育部门。
- 第一任务：将零散古籍材料转化为有出处、可互动、可持续扩展的数字风味展项。
- 差异化：非遗饮食题材、沉浸式考古局世界观、可见证据链、双菜规则融合与离线展项交付闭环。
- 明确边界：融合结果是离线规则推演，必须展示来源、继承特征、现代创新、风险和专家复核状态，不替代学术定论或厨师试做。
- 文案原则：不以“AI”作为卖点，不展示泛化功能清单，以一宗真实策展任务证明产品价值。

## 核心体验

### 首屏结构

首页是一宗“南宋风味数字展项”策展委托，桌面端在第一视口同时呈现四层信息：

1. 委托简报：委托编号、委托方、原始材料与交付目标。
2. 研究对象：可旋转、可拆解、可切换历史和现代模式的蟹酿橙 3D 藏品。
3. 融合预告：`蟹酿橙 × 玉糁羹 → 蟹粉橙香米羹`，展示父本、继承技法、现代转译和待复核标记。
4. 交付闭环：`古籍线索 → 证据复原 → 菜品融合 → 数字展项`。

品牌名“风味考古局”仍是第一视口中的一级标题，“从复原到新生”作为支持主张。首屏底部保留下一段内容的视觉提示，避免形成封闭海报。

### 评委路径

- 主命令“接手这宗风味案”进入现有五阶段可信复原流程。
- 次命令“查看融合推演”直接打开馆藏库的互动研究视图，并预选风味进化、蟹酿橙与玉糁羹。
- 用户完成复原后仍可通过馆藏和互动研究选择任意其他父本，不把首页示例变成唯一可用组合。
- 合作展厅继续承接商业闭环，说明离线单文件、馆藏数据、展项脚本、规则包和研学材料等实际交付物。

## 视觉系统

视觉方向为“南宋档案室 × 当代策展控制台”。页面保持克制的博物馆工作界面，不做通用科技大屏或营销卡片墙。

- 墨黑承担研究空间，宣纸白承载档案信息，朱砂红用于命令与委托盖章。
- 青铜绿只标识可信证据，明黄只标识融合新生结果，形成明确的语义对比。
- 3D 藏品保持全幅、无装饰卡片容器，并叠加档案编号、证据引线与朱砂批注。
- 融合预告使用两个父本档案向结果汇合的构图，真实馆藏图片只出现在父本位置。
- 控件继续使用现有 Lucide 图标、4px 圆角和稳定尺寸；不会用文本胶囊代替熟悉图标。
- 不引入外部字体、图片、模型、脚本或网络请求，维持单文件离线交付与 3,000,000 字节上限。

### 动效与响应式

首次进入按“委托盖章、古籍证据展开、3D 藏品显现、父本汇合”依次出现，总时长约 1.2 秒。动效只使用 CSS 和已有 Three.js 场景，不增加运行时依赖。

在 `prefers-reduced-motion: reduce` 下取消位移、缩放和循环动画，只保留即时状态切换。手机端按“委托、3D、融合结果、闭环”纵向排列；3D 热点、模型控件、主命令和底部导航必须保持独立操作区域，不能重叠或产生非预期横向滚动。

## 组件与状态设计

### `HomeExhibit`

负责首页整体语义和区域编排，继续连接现有 `CrabOrangeStage` 与博物馆会话。首页本身不复制融合规则。

### `FeaturedFusion`

新增首页融合预告组件，调用 `fuseDishes('dish_001', 'dish_003')` 获取真实规则结果，并从馆藏数据读取两道父本的名称、朝代、地域、技法和本地图片。组件只负责展示和触发“查看融合推演”。

### 会话动作 `openFusion`

在 `museumSessionReducer` 中新增原子动作，一次完成以下状态：

- `activeExhibit = 'archive'`
- `archiveTab = 'research'`
- `researchTool = 'evolution'`
- `selectedDishId = 'dish_001'`
- `secondaryDishId = 'dish_003'`

使用单一动作避免多个 dispatch 之间出现短暂错误页面，也让直接跳转行为可独立测试。

### `EvolutionExhibit`

第二父本改为读取和更新共享的 `secondaryDishId`。进入首页示例时直接显示玉糁羹和可推演状态；用户选择新父本或重置时同步更新会话。融合计算仍由现有 `fusionEngine` 完成。

## 数据与异常处理

- 首页示例使用现有明确规则：蟹酿橙与玉糁羹生成蟹粉橙香米羹。
- 若明确规则不可用，沿用确定性回退，但首页和结果区必须显示“待专家复核”，不得把回退描述成已证实结论。
- 本地图片缺失时显示文字档案和稳定占位背景，不阻塞融合操作。
- WebGL 初始化失败时继续使用现有 2.5D 降级展台，首屏信息和两个命令仍可操作。
- React 运行时异常继续交由现有可恢复错误边界处理。

## 测试与验收

开发遵循测试先行：先写失败测试并确认失败原因，再实现最小改动。

自动化覆盖：

- 首页包含“从复原到新生”、策展委托、完整闭环和融合预告。
- `openFusion` 原子动作产生预期的五项会话状态。
- 首页示例通过真实融合引擎返回“蟹粉橙香米羹”。
- `EvolutionExhibit` 读取、修改和重置共享第二父本。
- 离线页面仍无外部资源、网络请求或新增模型文件。
- 减少动态效果、移动安全区和打印规则继续有效。

发布验收：

- 离线专项测试、前端全量测试、脚本测试、lint 和正式构建全部通过。
- 单文件 HTML 小于 3,000,000 字节，ZIP 可正常读取。
- Chrome 与 Edge 在 1440×900、1280×720、390×844 三个视口验收首页、融合直达和 WebGL 降级。
- Canvas 非空且交互会改变像素；桌面和手机页面无控件重叠、文本截断或非预期横向滚动。
- 重新生成产品截图、验证报告与最终提交包。

## 不在本轮范围

- 不增加在线模型调用、Agent、知识库服务或后端接口。
- 不生成新的菜品图片、3D 模型或外部字体。
- 不扩展融合规则库，也不承诺融合菜已经完成厨师试做或专家审核。
- 不重构可信复原、馆藏或合作展厅中与首页闭环无关的代码。
